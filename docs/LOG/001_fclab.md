# LOG 001 — FcLab（ファミコン表現の見本市）

期間: 2026-08-01
リポジトリ: Sekiguchi-Takashi/FcLab
最終バージョン: v1.9

## 目的

本番のゲームを決める前に、Claudeがプログラム描画でどこまでの表現を出せるかを一望する。
9章（後に11章）の表現デモを1本のAPKにまとめ、実機で触って採否を判定する。

## 結果

### 表現技法（1〜9章）

全て「使う」で確定。詳細は `RULE_ART.md` の5節。

### ドットの限界（0章）

同一被写体を各サイズ・各色数で比較。

| サイズ | 判定 |
|---|---|
| 32 | 何とか分かる |
| 48 | 何とか分かる |
| 64 | 識別可能 |
| 96 | 特徴まで分かる |

| 色数 | 判定 |
|---|---|
| 8 | 分からない |
| 16 | 分かる |
| 32 | 分かる |

### 画面解像度

| 解像度 | 判定 |
|---|---|
| 256x240 | 粗い |
| 384x216 | 見える |
| 640x360 | 同じ |
| 960x540 | クリア |

→ **640x360を採用**。960はドット絵にする意味が薄れるため不採用。384は操作性都合の代替案として残す。

### 写真背景＋ドットキャラ（10章）

判定: **良**。役割を分ければ違和感なく成立する。

## 得られた知見

**荒く見える原因は画面解像度であって、スプライトサイズではない。**
256x240の画面を高解像度端末に引き伸ばすと、1ドットが5〜8物理ピクセルの巨大な四角になる。スプライトを大きくしてもこれは変わらない。効くのは順に **画面解像度 > 色数 > スプライトサイズ**。

**ファミコン基準（3色）は写真由来の素材では成立しない。**
手描きのドット絵なら3色で成立するが、写真を減色したものは8色でも識別できなかった。

**Claudeの弱点は解像度ではなく造形。**
ドットを細かくするほど「絵として上手いか」が問われる。色数を増やすほうが、弱点を突かずに質を上げられる。

## 開発上の失敗と対策

**CIを組む前に開発を始めたのが最大の失敗。**
初日、Godot Androidエディタを実機に導入し、ZIPを展開してエディタで開く方式を取った。結果、Parse Error の一次発見者がユーザーになり、2時間を消費した上に一度Godotを断念する判断まで誘発した。

CIを先に通せば、スクリプトエラーはClaudeがログで読める。以後は「作る→CIが焼く→ユーザーはAPKを触るだけ」の形が成立した。**新規プロジェクトでは必ずフェーズ0（ビルド疎通）から始める。**

**手作業パッチ（sed）をユーザーに渡してファイルを破壊した。**
以後、修正は必ずZIPを作り直して配布する。

**型推論エラーでCIが4回落ちた。**
原因のパターンは4つに分類でき、`RULE_CODE.md` の2節に規約化した。同種の危険を機械的に洗い出すチェックを開発側に組み込んだ。
